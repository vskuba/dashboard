# dashboard — общие страницы панелей: разметка, стили, скрипты и их Python

Подключается submodule-ом в проекты рядом с `py_modules`:

```
<проект>/
  py_modules/   ← инструменты
  dashboard/    ← страницы панели целиком: вид и его Python
```

## ⚠⚠ Граница проходит по предмету, а не по языку

Раньше она шла по языку: «`py_modules` — только Python, здесь — только разметка».
Правило выглядело простым, но резало страницу пополам: разметка ехала сюда, а
её ручки и хранилище оставались там, то есть **общая страница не была целой ни в
одном репозитории**. Подключить её к соседу значило собрать половинки из двух
мест и не забыть ни одной.

Теперь так:

| | Где | Почему |
|---|---|---|
| страница панели: разметка, стили, скрипты, **её ручки, хранилище и прогоны** | **здесь** | это один предмет, и меняется он целиком |
| инструменты: база, HTTP, браузер, файлы, картинки, ssh | `py_modules` | ими пользуется и панель, и крон, и скрипт в терминале |

Признак простой: **модуль про показ панели — сюда; модуль, которым работают
откуда угодно, — в `py_modules`.** Раздача статики (`panel_static`) и загрузчик
шаблонов — пограничны по виду, но по предмету это механика панели.

⚠ Обратное направление тоже действует: предметный инструмент сюда не кладут,
даже если им пользуется одна-единственная страница. Запрос к базе, поход по ssh,
разбор PDF — это `py_modules`, и страница их просто зовёт.

### Скелет панели — тоже здесь

Вход, люди, настройки, бэкап, seed, раздача статики и загрузчик шаблонов лежат в
`src/panel/`. Раньше они жили в `dashboard/src/panel/`, и получалось расщепление:
ручки настроек в слое, а сама страница настроек здесь.

Признак проверен, а не взят на веру: `panel_*` **не зовёт ни один крон, воркер
или бот** ни в одном из трёх проектов — только веб-процесс.

⚠ Имена функций при переезде не менялись (`panel_auth_need` остался собой):
namespace «папка + имя файла» даёт тот же префикс, что и прежний каталог.
Сменился только путь импорта.

## Состав

```
css/        общие стили
js/         общие модули страниц
template/   общие шаблоны страниц
src/page/   Python страниц: ручки, хранилище, прогоны
src/panel/  скелет панели: вход, люди, настройки, бэкап, статика, шаблоны
```

Каталог на страницу, модуль на часть:

```
src/page/e2e/e2e_store.py        -> e2e_store_run_list()
src/page/journal/journal_api.py  -> journal_api_router()
src/panel/panel_auth.py          -> panel_auth_need()
```

Namespace — «папка + имя файла», как в `py_modules/docs/code_rules.md`, § 1.
Промежуточный `page/` в префикс не входит: он говорит, что это страницы, а не о
предмете модуля.

⚠⚠ **Имя модуля страницы сверяют с `py_modules`.** Совпадёт — и в одном дереве
окажется два `journal_catch`, которые уже ничем не различить:

```bash
find py_modules -name "<имя>.py" -not -path "*__pycache__*"
```

Так разошлись две пары: застава журнала (механизм в слое — `journal_catch`,
подключение здесь — `journal_install`) и Cronicle (инструмент в слое —
`cronicle_api`, страница здесь — `cronicle_page_api`).

## Как проект это получает

### Статика и шаблоны: «сперва свой, потом здесь»

Раздача ищет файл **сперва у себя, потом здесь** — путь страницы не меняется:

```python
from dashboard.src.panel.panel_static import panel_static_files

app.mount('/static', panel_static_files(own_public, shared='dashboard'),
          name='static')
```

### Python: импорт идёт от корня проекта

Правка `PYTHONPATH` **не нужна** — ни одной. Каталог подключён submodule-ом рядом
с кодом проекта, то есть уже лежит под корнем, который в пути поиска есть всегда:

```python
from dashboard.src.page.journal.journal_api import journal_api_router
```

⚠⚠ **Так сделано не из экономии строк, а чтобы `src` не сталкивались.** Сперва
`/app/dashboard` клался в `PYTHONPATH` (в двух `dockerfile` и в `pythonpath`
теста) — и тогда здешний `src/` сливался с `src/` проекта в **один**
namespace-пакет. Проверено: `import src` даёт
`_NamespacePath(['/app/src', '/app/dashboard/src'])`. Работает, но вопрос «где
лежит `src.что-то`» перестаёт иметь один ответ, а файл с совпавшим именем молча
перекрывает чужой.

⚠ Цена приёма: **имя каталога submodule стало частью пути импорта**. Подключи его
проект под другим именем — импорты не найдутся. У всех проектов он `dashboard/`,
так что сегодня это не стоит ничего, но знать стоит.

⚠⚠ **Порядок каталогов — договор.** Свой каталог проекта идёт первым, и это
единственный способ отойти от общего вида, не ломая остальных: положил у себя
файл с тем же именем — он и отдаётся. Переставь порядок, и такая правка молча
перестала бы действовать.

⚠⚠ **У того же свойства есть обратная сторона: случайное столкновение имён.**
Общий `js/setting.js` страницы настроек налетел на уже существовавший в проекте
`js/setting.js` — модуль пользовательских настроек. Проект выиграл, страница
получила чужой скрипт: 901 байт вместо 238 строк, пустая таблица **без единой
ошибки в консоли**. Отсюда правило: скрипт страницы зовут `<страница>_page.js`,
если короткое имя уже занято общим модулем, — и перед переносом сверяют:

```bash
ls data/uvicorn/public/js/<имя>.js data/uvicorn/public/css/<имя>.css
```

Пример живой: `css/common.css` совпадает у двух проектов и лежит здесь, а у
третьего свой — он его и видит.

⚠⚠ **И третья сторона: молчаливая опора на глобаль проекта.** Общий модуль зовёт
`loadTz()` — а скрипт, который её объявляет, подключал `base.html` **одного**
проекта. У соседа страница «Тесты → E2E» не работала вовсе:
`ReferenceError: loadTz is not defined`, вёрстка при этом рисовалась, и обе
колонки навсегда стояли в «Загрузка…» — ни отказа, ни записи в журнале.

Отсюда правило: **общая страница везёт свои зависимости сама**. Нужен
`tz.js` — шаблон каркаса подключает его строкой перед своим модулем, а не
надеется, что проект уже это сделал. Проверка простая: открой страницу у
соседа и посмотри консоль, а не только кадр, — такая поломка кадром не видна.

## ⚠ Что сюда кладут

Два разных случая, и путать их не надо.

**Файл, который уже совпадает** у двух проектов и дальше должен меняться у обоих
сразу. Не «похож», а совпадает — сверка по контрольной сумме. Так сюда попали
первые 347 строк:

| файл | у кого совпадал |
|------|-----------------|
| `js/notification.js`, `css/notification.css` | все три |
| `js/modal.js`, `css/modal.css` | у двоих, у кого они есть |
| `css/common.css` | у двоих из трёх |
| `js/tz.js` | был у одного, а звали его общие страницы — см. ⚠⚠ выше |
| `js/sidebar_resizer.js` | у двоих, **и копии разошлись** — см. ниже |

⚠⚠ **Разошедшиеся копии сводят по богатой.** `sidebar_resizer.js` жил у двух
проектов: у одного только вертикальный разделитель, у второго — две оси, сброс
двойным кликом и предел по размеру окна. В каркас уехал второй: его API
включает первый целиком, так что проект, знавший одну функцию, не заметил
перехода, а проект с тремя не потерял двух.

Взять «ту, что проще» значило бы молча отнять работающий функционал у второго —
и узнал бы он об этом не отказом, а тем, что разделитель перестал
восстанавливаться.

**Страница целиком, которую заводят общей намеренно** — чтобы соседи получили её
подключением, а не копией. Такая приезжает сразу со своим Python и обязана быть
подключаемой в несколько строк: предметное знание установки (каталог прав, имена
таблиц, пункт меню) приходит доводом, а не зашивается.

⚠⚠ **Общей считается та, что завелась у второго проекта.** Пока страница живёт
в одном, она не общая, а просто лежит в чужом репозитории: ни один довод ещё не
проверен на чужой установке, и первое же подключение их переделывает.

## ⚠⚠ Что сюда не кладут

**Страницу, похожую на 72%.** Замер `base.html`: DatingAi ↔ PersonaAI 72%,
а с RhapsodyAi 17% и 22%. Это не каркас с тремя наполнениями, это две близкие
панели и одна чужая. В оставшихся 28% лежит ровно то, ради чего страница
существует — состав меню и разделы, — и общий каркас пришлось бы
параметризовать блоками до состояния, когда правка меню требует смотреть в три
места.

Каркас появится здесь, когда будет что обобщать: либо у двух панелей совпадёт
скелет страницы целиком, либо заводится третья панель и ей нужен старт.

**Предметные стили.** `dating_page.css`, `photo_*.js` — они про свой проект,
даже если выглядят типовыми.

**Каталог прав.** `workflow:view`, `e2e:run` — это имена чужих предметных
областей; модуль с ними перестаёт быть переносимым. Права приходят доводом:
общая страница знает, что право нужно, и не знает, как оно зовётся
(`py_modules/docs/panel.md`, § 1).

**Миграции.** Схему каждая установка накатывает себе сама: у каждой свой движок
миграций, свой порядок и свои сроки.

⚠ Но **эталон таблиц кладут сюда**, рядом с кодом, который их требует
(`src/page/e2e/schema/e2e_tables.sql`). Его никто не применяет — он для
переноса. Без него второй проект копирует DDL у первого, и тот уже совпадал
байт в байт у двух установок: разошлись бы на первой правке схемы.

## Правка

Правка здесь — правка всех проектов, где файл не перекрыт своим. Поэтому:

1. коммит в этот репозиторий **и push**;
2. в проекте отдельным осознанным коммитом двигается указатель submodule.

⚠⚠ Порядок не переставить, и цена уже заплачена: указатель, уехавший в проект
раньше, чем коммит сюда, **роняет выкладку** — `fatal: remote error:
upload-pack: not our ref`. Сборка не может забрать коммит, которого в origin
нет, и падает на `git submodule update`, то есть до всего остального.

⚠ Перед пушем проекта стоит убедиться, что указатель достижим:

```bash
git -C dashboard fetch origin
git -C dashboard branch -r --contains "$(git -C dashboard rev-parse HEAD)"
```

Пусто — коммит ещё не в origin, пушить проект рано.
